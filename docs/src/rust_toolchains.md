# Toolchains

A Rust build in Bazel selects its compiler, standard library, and companion tools
through a set of registered [Bazel toolchains][bazel_toolchains]. `rules_rust`
ships one toolchain type per companion tool so that Rust, `rust-analyzer`, and
`rustfmt` can be resolved independently.

[bazel_toolchains]: https://bazel.build/extending/toolchains

Most users register toolchains via the `rust` module extension (see
[Bzlmod](./rust_bzlmod.md)) rather than declaring these rules directly. The rules
below exist for users who need to define custom toolchains — for example, to point
at a locally built `rustc` or to add a target triple that the extension doesn't
cover.

## Toolchain rules

- [rust_toolchain](./rust_toolchain.md) — Declare a Rust compilation toolchain: the
  `rustc` binary, standard library, linker, and per-target compilation settings.
- [rustfmt_toolchain](./rustfmt_toolchain.md) — Declare a toolchain providing the
  `rustfmt` binary used by [rustfmt](./rustfmt.md) rules.
- [rust_analyzer_toolchain](./rust_analyzer_toolchain.md) — Declare a toolchain
  providing the `rust-analyzer` binary and proc-macro server used by the
  [rust_analyzer](./rust_analyzer.md) integration.

## Data rules

- [rust_stdlib_filegroup](./rust_stdlib_filegroup.md) — Group the files of a Rust
  standard library archive into a target that can be attached to a
  `rust_toolchain` via the `rust_std` attribute.

## Platform constraints

The `rust` module extension derives the `exec_compatible_with` and
`target_compatible_with` constraints of each toolchain from its Rust target triple
(see `triple_to_constraint_set` in `@rules_rust//rust/platform:triple_mappings.bzl`).
The CPU and OS components map to constraints from `@platforms`. The same
constraint sets back the `@rules_rust//rust/platform:<triple>` `config_setting`s
used in `select()` statements, e.g. in the `BUILD` files generated by
`crate_universe`.

### glibc vs musl

Linux `musl` triples (`*-linux-musl`, `*-linux-musleabi`, ...) additionally require
`@platforms_contrib//os/linux/libc/musl:available` from
[platforms_contrib][platforms_contrib]. A musl toolchain is therefore only selected
for platforms which declare that musl is available:

```python
platform(
    name = "linux_x86_64_musl",
    constraint_values = [
        "@platforms//cpu:x86_64",
        "@platforms//os:linux",
        "@platforms_contrib//os/linux/libc/musl:available",
    ],
)
```

[platforms_contrib]: https://github.com/bazel-contrib/platforms_contrib

`gnu` triples deliberately do **not** require
`@platforms_contrib//os/linux/libc/glibc:available`: Bazel's default host platform
(`@platforms//host`) does not declare any libc, so doing so would prevent the
default toolchains from resolving. As a consequence a glibc toolchain also matches
musl platforms, and when both a glibc and a musl toolchain for the same CPU are
registered, Bazel uses whichever was registered first (`register_toolchains("@rust_toolchains//:all")`
registers toolchains in alphabetical order, i.e. `gnu` before `musl`).

To make the two mutually exclusive, constrain the glibc toolchain to
`@platforms_contrib//os/linux/libc/glibc:available` via `rust.repository_set` and
use a host platform which declares glibc as available, e.g.
`@platforms_contrib//host` or a custom platform with `parents = ["@platforms//host"]`.
See [`examples/cross_compile_musl`](https://github.com/bazelbuild/rules_rust/tree/main/examples/cross_compile_musl)
for a complete setup.
